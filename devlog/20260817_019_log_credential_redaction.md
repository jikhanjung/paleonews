# 로그 자격증명 마스킹 (0.3.2) — 소급 기록

**날짜**: 2026-08-17 (릴리스 당일)
**기록 시점**: 같은 날 늦게. 릴리스 당시엔 `DEPLOY.md` 델타만 남고 devlog 가 없어 소급 작성한다.
**근거**: 커밋 `967c525`, `DEPLOY.md` 0.3.2 행.
**후속**: 이 수정은 0.3.7 에서 한 번 **되돌아갔다** — `devlog/20260817_018_p2_django_port.md` 참조.

## 무슨 일

python-telegram-bot 은 API 를 httpx 로 호출하고, httpx 는 요청 URL 전체를 INFO 로 찍는다.
그런데 Telegram 은 봇 토큰을 URL **경로**에 담는다:

```
httpx: HTTP Request: POST https://api.telegram.org/bot<id>:<token>/getUpdates
```

봇은 10초 주기로 폴링한다 → 폴링마다 살아있는 토큰이 로그에 평문으로 쌓였다.

**운영 실측**: `/srv/paleonews/logs` 의 파일 4개에 **104,075건**. 퍼미션은 `0664`(세계 읽기).

토큰은 "민감한 값"이 아니라 **그대로 제시하면 인증이 되는 값**이다. 그 파일을 읽을 수 있는
사람은 봇을 그대로 조종할 수 있었다.

## 수정

`log_redact.RedactingFilter` 를 **로거가 아니라 핸들러**(콘솔·파일)에 붙였다. 로거 이름과
무관하게 나가는 모든 레코드를 덮기 위해서다 — 정작 로깅하는 주체가 우리 코드가 아니라
서드파티(httpx)이기 때문이다.

두 가지가 핵심이었다:

- **포맷된 메시지를 가리고 `record.args` 를 비운다.** httpx 는 `%s` 로 지연 포맷하므로
  args 를 남겨두면 포맷 단계에서 원문이 되살아난다.
- **봇 ID 는 남기고 토큰 본문만 가린다.** ID 만으로는 API 를 호출할 수 없고, 남겨야 어느 봇인지
  추적이 된다 → `bot<id>:<redacted>`.

쿼리스트링 비밀값(`api_key=`, `token=` …)과 `Bearer` 헤더도 같은 필터가 덮는다.

## 이미 쓰인 로그

필터는 **새 유출만 막는다.** `scripts/redact_existing_logs.sh` 가 과거분을 정리한다:
멱등이고, 로테이션 중 inode 를 유지하려 in-place 로 고치며, 파일 퍼미션을 `0640` 으로 조인다.
실제 로그 200줄 표본으로 검증 — 400건 → 0건, 다른 내용과 줄 수는 불변, 재실행은 no-op.

## 남은 위험 — 토큰 재발급

커밋은 "BotFather 에서 토큰을 재발급해야 한다"고 적었다. **파일을 지워도 과거 노출은
되돌려지지 않기 때문이다.**

다만 `DEPLOY.md` 0.3.2 행에는 같은 날 **재발급하지 않기로 결정**했다고 기록돼 있고,
"추후 재검토 대상으로 남긴다"고 덧붙였다. 두 기록이 어긋나는 게 아니라 순서다 —
권고가 있었고, 그 위에서 운영자가 판단했다. **재검토 항목으로 살아 있다.**

## 교훈 (0.3.8 이 증명한 것)

이 마스킹은 **CLI 의 `setup_logging()` 이 핸들러에 붙이는 방식**이었다. 그래서 로깅 설정을
누가 하느냐가 바뀌면 통째로 사라진다 — 실제로 0.3.7 에서 봇이 `manage.py bot` 으로 바뀌며
Django `LOGGING` 이 그 설정을 밀어냈고, 토큰이 다시 평문으로 찍혔다.

> **자격증명 마스킹은 "붙였다"가 아니라 "이 프로세스의 로깅 설정에도 붙어 있나"로 검사해야 한다.**
> 0.3.8 이 그 검사를 테스트로 넣었다(선언 검사 + 실제 `dictConfig` 적용 후 마스킹 확인).
