P0(특성화 테스트) → 모델 → 런타임. naverland 에서 통한 순서를 그대로 따랐다.

전환 자체는 세 릴리스로 나눴다 — 성격이 다른 변경을 한 릴리스에 묶으면 문제가 났을 때
어느 쪽인지 못 가린다:

| | 내용 |
|---|---|
| **0.3.6** | `db.py:_migrate()` 레거시 경로 수정 (운영 영향, Django 무관) |
| **0.3.7** | Django 전환 |
| **0.3.8** | 0.3.7 이 낸 로그 마스킹 회귀 긴급 수정 |

## 패리티 증명

`client` 픽스처를 `params=["fastapi", "django"]` 로 파라미터화해, **같은 특성화 테스트가 두
구현에 그대로 적용된다**. 138개 통과. 변이 확인: Django 쪽 키워드 `*` 처리와 중복 chat_id
가드를 각각 지우면 `[django]` 만 실패하고 `[fastapi]` 는 통과한다.

템플릿은 **Jinja2 그대로 재사용**했다(Django 의 Jinja2 백엔드). Django 템플릿 언어로 옮기지
않은 이유: `|map(...)` 처럼 인자를 받는 필터가 DTL 에 없어 5개를 전부 손봐야 하고, 그 과정이
곧 "화면이 조용히 달라지는" 경로다. admin 은 DjangoTemplates 엔진을 따로 쓴다.

## 테스트가 못 잡고 **컨테이너가 잡은** 것 둘

이미지를 빌드해 운영 데이터 사본에 붙여보고서야 나왔다. 둘 다 원인과 **테스트 공백**을 함께 고쳤다.

1. **전 화면 500.** Jinja2 `DIRS` 가 `BASE_DIR / "paleonews" / "templates"` 였는데, 이미지에선
   `paleonews` 가 site-packages 에 설치돼 그 경로가 없다. repo 에서는 멀쩡하고 이미지에서만
   죽는다 — **0.3.3(템플릿이 wheel 에서 빠져 5화면 500)과 정확히 같은 모양**이다.
   설치된 패키지 기준(`Path(paleonews.__file__).parent`)으로 바꿨다.
2. **전 POST 403.** admin 이 `CsrfViewMiddleware` 를 요구하는데 템플릿엔 토큰 필드가 없다.
   레거시 뷰만 `@csrf_exempt`(이전에도 CSRF 보호는 없었다). 그리고 **테스트 클라이언트를
   `enforce_csrf_checks=True`** 로 바꿔 이 부류가 앞으로는 테스트에서 걸리게 했다.

> 교훈: 이 둘은 "테스트 환경과 이미지 환경의 차이"라는 한 부류다. `/healthz` 는 양쪽 다 200 이었다.

## 넘었다가 되돌린 선 — 인증 태세

처음엔 5화면 전부에 `@login_required` 를 걸었다. 그건 "admin 도입"이 아니라 **인증 태세 변경**
이고, 슈퍼유저를 만들기 전까지 운영자가 UI 에서 잠긴다. 패리티로 되돌렸다 — `/admin/` 만
로그인을 요구하고 기존 화면은 그대로 열려 있다. 잠그려면 뷰당 데코레이터 한 줄이고,
그때 슈퍼유저 생성이 배포 절차에 들어간다.

## 곁다리로 잡은 운영 버그 (0.3.6)

Django 스캐폴딩 후 CLI 가 도는지 보다가 `_migrate()` 가 크래시했다. `git stash` 로 재현해보니
**내 변경 탓이 아니라** 그 경로가 그만큼 오래된 DB 에서 실행된 적이 없었을 뿐이고,
**운영 DB 가 바로 그런 DB 였다.** 네 가지가 겹쳐 있었다(상세는 커밋 `ce728df`):

`SELECT *` 컬럼 순서 어긋남 / rename 자체 커밋 탓에 반쯤 마이그레이션된 상태로 굳음 /
크래시가 남긴 `users_new` 잔재로 **DB 를 다시 못 엶** / FK 켠 채 DROP 이라 **발송 이력 있는
모든 실제 DB 가 실패**.

가설이 아니었다 — 운영의 `users.telegram_chat_id` 가 여전히 NOT NULL 이어서 웹 UI 의
"이메일 전용 사용자 추가"가 실제로 500 이었다. 운영 사본 리허설 후 배포했고,
dispatch 784건이 전부 user_id 를 유지한 채 재구축이 완주했다.

## 내가 낸 회귀 (0.3.8)

0.3.7 배포 후 컨테이너 로그를 보다 발견: **텔레그램 토큰이 다시 평문으로** 찍히고 있었다.
0.3.2 의 마스킹은 CLI `setup_logging()` 이 핸들러에 붙이는 방식인데, 봇이 `manage.py bot` 으로
바뀌며 **Django `LOGGING` 이 그 설정을 밀어냈다**. 폴링 주기가 10초라 2분 만에 여러 건이 남았다.

Django `LOGGING` 에 필터를 넣어 **Django 로 도는 모든 프로세스**(봇·run_pipeline·gunicorn)를
덮게 했다. 노출은 docker json 로그뿐이고 컨테이너 재생성으로 소멸했다(파일 로그는 CLI 경로만
써서 필터가 유지됐다). 회귀 테스트 2건 — 선언 검사 + **실제 dictConfig 적용 후 마스킹 확인**
(선언만 보면 "붙였는데 안 먹는" 경우를 놓친다).

> **이건 테스트가 아니라 배포 후 실물 확인이 잡았다.** 그래서 매 배포마다 `/healthz` 말고
> 실제 페이지와 로그를 본다.

## 유지한 제약 (P06 보류 사유들)

- **단일 컨테이너 all 모드**(cron+bot+web, root) — 서비스를 쪼개면 `claude_code` 구독 인증
  표면이 늘어 0.2.8 에서 복구한 과금이 깨진다. `ANTHROPIC_API_KEY` 는 여전히 넣지 않는다.
- **gunicorn worker 1개** — `_pipeline_status` 가 프로세스 로컬이라 worker 가 둘이면
  "실행 중" 표시와 409 중복 방지가 worker 마다 갈린다. SQLite 쓰기 주체도 안 늘린다.
- **`app_settings` overlay 유지** — Django settings 로 옮기지 않는다(P06 사유 ④).
- **admin 이 안 덮는 화면은 전용 뷰로 남김**(P06 사유 ③): 파이프라인 버튼·상태 폴링,
  provider·모델 드롭다운, 사용자별 키워드.

## 백업 반출 위생 (같이 처리)

admin 도입으로 `django_session` 이 생겼다 = **bearer 토큰 테이블**. 계약 MUST 에 따라
hourly 스냅샷에서 지운다(`sanitize_egress`, fsis2026 동형). 라이브 DB 는 건드리지 않고,
VACUUM 까지 해서 토큰이 free page 에도 안 남는다. 비밀번호 해시는 남긴다(성질이 다르다).
위생이 실패하면 스냅샷을 채택하지 않는다 — 세션 실린 사본을 남기느니 백업을 거른다.

초크포인트를 hourly 에 둔 이유: 하위 트랙(오프사이트·미러·수동 scp)이 전부 이 산출물을
소비하므로 한 번 지우면 **구조적으로** 덮인다.
